Forecast assumptions and execution boundary
  • The database executes customer filters, joins, discounted line calculations and daily aggregation.
  • Node groups those daily totals into months and forecasts outside the Substrait plan. This is explicit application processing, not automatic query folding.
  • All segments share the unfiltered observation range. Both boundary months are excluded because the sample may cover only part of each month.
  • Interior months without sales count as zero, assuming the supplied sample is complete. Missing source data cannot be detected here.
  • Each forecast month uses the same average of the last three training months. No seasonality model or prediction interval is implemented.
  • Amounts remain decimal strings with BigInt calculations. Only chart coordinates use floating-point numbers. Display values round to cents, half away from zero.
  • Revenue = unit price × quantity × (1 − discount). Freight is excluded. Orders without a matching customer, date or detail line contribute no revenue.

Implemented query controls and limits
  • Only the listed stages and backends are accepted. Requests cannot supply SQL, table names or arbitrary expressions.
  • The catalog and supported Substrait profile validate the compiled plan. Literal filter values are bound separately.
  • One request runs at a time. More than 5,000 daily rows rejects forecasting rather than silently truncating it.
  • Each execution requests a 10-second query timeout. This is not an end-to-end deadline for compilation, pool waits or failed cancellation.
  • This server binds only to loopback and checks origin/host. These checks are not user authentication.

The same P75 can round differently
0.75 is exactly representable in binary. The issue here is the selected computation type: decimal inputs can enter a floating-point percentile calculation.
Untyped fraction
PERCENTILE_CONT(value, 0.75)
  OVER (PARTITION BY country)
Observed result type: FLOAT64
Explicit decimal fraction
PERCENTILE_CONT(value, NUMERIC '0.75')
  OVER (PARTITION BY country)
Observed result type: NUMERIC

The comparison uses the same order values and country groups. Only the percentile fraction's type changes. Some float formatting hides the representation difference, even when rounding exposes it.
The decision: define numeric type, rounding mode and rounding stage for the metric. A one-cent difference may be acceptable in an exploratory chart and unacceptable in a reconciliation. Decimal precision alone does not establish accounting correctness.
Golden's BigQuery decimal path uses a typed BIGNUMERIC fraction for its bounded decimal contract. An IR can carry that choice, but correct SQL can also express it directly.
