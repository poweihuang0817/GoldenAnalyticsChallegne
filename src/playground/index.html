Our constraints, checked by TypeScript


1. Declare the column type
// Catalog entry
{ name: 'city', type: 'string', nullable: true }

// Inferred expression type
customers.columns.city // Expr<'string', true>
2. Define the operation constraint
lower(this: Expr<'string', N>): Expr<'string', N>;
Actual signature from src/api.ts. The receiver must be a string expression. N preserves whether the value can be NULL.
3. TypeScript checks each call
// Accepted: city is a string expression.
customers.columns.city.lower();

// Type error: order_id is an i32 expression.
orders.columns.order_id.lower();
We encode the rule in the API. The editor and tsc report incompatible calls before a database query runs.
The method exists on Expr, but its this constraint rejects a numeric receiver. Runtime validation remains necessary when static types are bypassed.
lower() builds an expression. The database performs the lowercase conversion later.






Projection: choose and name output columns


Input → output
// Illustrative input row
{ customer_id: 'ALFKI', city: 'Berlin', country: 'Germany' }

const projected = customers.select({
  customer_city: customers.columns.city
});

// Corresponding output row when executed
{ customer_city: 'Berlin' }
The object key is the output name. The value is the source expression. This selects city, renames it, and leaves out customer_id and country.
select() chooses columns; filter() chooses rows. This projection keeps one output row per input row, including duplicates.
The next stage has a new schema
projected.columns.customer_city; // Accepted
projected.columns.city;          // Type error
projected.columns.customer_id;   // Type error

// Conceptual SQL
SELECT city AS customer_city FROM customers
The original customers relation is unchanged. Building projected has not executed SQL.
Actual select() type constraint
select<E extends Record<string, Expr>>(expressions: E & KnownKeys<E>): Table<Output<E>>;
E is the projection object. Its values must be expressions; KnownKeys requires statically known output names. Output derives each expression's type and nullability for the returned Table.

Why composition matters
First sum quantities per order. Join those totals back to all orders, replace missing totals with zero, then average. Averaging detail rows directly would answer a different question.
Each transformation returns a new Table and leaves its input reusable. Filter preserves columns; select defines output columns; aggregate exposes group keys and named measures.
Expr versus Measure
An Expr describes a row value. A Measure, such as count() or sum(), aggregates rows. The result of aggregate() is a new relation whose columns can be used again.
Window extension: rank within each customer, then filter the ranks. Golden preserves the required SQL boundary while merging compatible operations.

} finally {

}
Why defer execution?
Building expressions describes work without fetching data. Queries can be composed and reused before choosing where to execute them.
execute() compiles and runs asynchronously. A separate compile() call is optional: it provides SQL and parameters for debugging and database-free compiler tests.
SQL and values travel together
SQL:        … lower(cast($1 as text))
Parameters: ['london']
The driver receives SQL plus ordered values. PostgreSQL uses $n placeholders; MySQL uses ? placeholders through the driver. Application code does not manually interpolate values.
Parameter values can be sensitive. Inspect deliberately; do not log them by default. Destroy the client after outstanding queries finish.






Separate the public API from SQL construction


Responsibilities
  1. Typed API: named expressions, composition and output types.
  2. Substrait subset: a standard relational representation.
  3. Golden lowering: validation, function mapping and SQL query boundaries.
  4. Kysely: SQL construction, quoting and parameters.
  5. Database: physical planning and execution.
Why retain an IR?
The relational boundary can accept a future frontend without exposing Kysely's SQL builder as the application contract. A semantic frontend would resolve metrics and relationships before producing relations.
The cost
Using Kysely directly would be simpler. Retaining Substrait requires Golden to implement and test relational-to-SQL lowering. Kysely can express the challenge queries too.
Current support is a constrained profile with Golden function extensions. It does not imply full Substrait interoperability, a semantic engine, or federation.






Result representation is part of the API


Counts and decimals
// London example: actual result shape
{ customer_count: '6' }

// Illustrative decimal representation
{ amount: '1234.5600000000' }
JavaScript number cannot exactly represent every 64-bit integer or decimal amount. Count/i64 and decimal outputs remain strings to avoid losing precision during result transport.
Caller responsibility
For further exact arithmetic, keep the calculation in the database or use a decimal library. Converting to Number is a deliberate precision tradeoff; adding strings concatenates them.
Explicit limits
The current decimal contract uses precision 38 and scale 10. A string preserves the returned value; it does not provide unlimited precision or undo rounding during computation.
Not every numeric result is a string. Floating-point results use numbers; some MySQL computed i32 values can arrive as strings, and inferred result types allow that representation.
The outer CAST(COUNT(*) AS text) implements this result contract. It is not a second aggregation or an extra subquery.






Portable intent needs explicit meaning


Chosen query interpretations
  • City: lowercase comparison, preserving accents and whitespace.
  • Units: average per-order totals; orders without details contribute zero.
  • Price: discounted merchandise; freight is counted once per order.
  • P75: continuous interpolation by the customer's country.
These are documented choices where the prompt is ambiguous. They are implemented by query helpers and supported functions, not inferred from a catalog or supplied automatically by Substrait.
How the contract is checked
  • Type-negative and runtime validation tests.
  • Independent expected calculations, including monetary arithmetic.
  • Real PostgreSQL/MySQL tests and DuckDB conformance.
  • Metamorphic checks: A AND B versus sequential filters.
  • SQL, ordered-parameter and lowering-trace snapshots.
Three backends agreeing can still hide a shared compiler bug. Independent oracles add another check. Unsupported operations are rejected explicitly.
These tests cover a supported subset; they are not a formal proof or exhaustive vendor conformance.

THE TRANSLATION BOUNDARY
Intent stays portable. Execution stays with the backend.



Public API
Table / Expr describes WHAT to compute. Immutable stages expose their own typed output schema.
Relational contract
Substrait is the supported IR, not the user interface. Validation rejects unsupported features; lowering preserves joins, ordering and aggregate grain.
Execution
Kysely constructs parameterized SQL. PostgreSQL/MySQL run remotely; DuckDB runs against a separately seeded local snapshot. No federation.


Future work: capability handling, authentication options and normalized errors. Semantic frontends and federation are not implemented.

Forecast assumptions and execution boundary
  • The database executes customer filters, joins, discounted line calculations and daily aggregation.
  • Node groups those daily totals into months and forecasts outside the Substrait plan. This is explicit application processing, not automatic query folding.
  • All segments share the unfiltered observation range. Both boundary months are excluded because the sample may cover only part of each month.
  • Interior months without sales count as zero, assuming the supplied sample is complete. Missing source data cannot be detected here.
  • Each forecast month uses the same average of the last three training months. No seasonality model or prediction interval is implemented.
  • Amounts remain decimal strings with BigInt calculations. Only chart coordinates use floating-point numbers. Display values round to cents, half away from zero.
  • Revenue = unit price × quantity × (1 − discount). Freight is excluded. Orders without a matching customer, date or detail line contribute no revenue.

The same P75 can round differently
0.75 is exactly representable in binary. The issue here is the selected computation type: decimal inputs can enter a floating-point percentile calculation.
Untyped fraction
PERCENTILE_CONT(value, 0.75)
  OVER (PARTITION BY country)
Observed result type: FLOAT64
Explicit decimal fraction
PERCENTILE_CONT(value, NUMERIC '0.75')
  OVER (PARTITION BY country)
Observed result type: NUMERIC

The comparison uses the same order values and country groups. Only the percentile fraction's type changes. Some float formatting hides the representation difference, even when rounding exposes it.
The decision: define numeric type, rounding mode and rounding stage for the metric. A one-cent difference may be acceptable in an exploratory chart and unacceptable in a reconciliation. Decimal precision alone does not establish accounting correctness.
Golden's BigQuery decimal path uses a typed BIGNUMERIC fraction for its bounded decimal contract. An IR can carry that choice, but correct SQL can also express it directly.
